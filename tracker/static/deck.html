01 · 问题

人在给 agent 当「人工状态管理器」

模式 A：先执行，后理解（现在）

  • 给一个模糊任务
  • agent 自主探索、改代码、跑命令
  • 产出大量代码 / 日志 / 执行记录
  • 人回头重读 context，判断它做对没有

执行成本被压缩了，理解与验证成本被推迟、并持续累积。

模式 B：先定义，再执行（要的）

  • 先写 spec：目标、边界、验收条件
  • agent 声明计划与验证方法
  • 分阶段执行，每阶段产出证据
  • 人只看偏差、关键决策和证据

差别不在「有没有计划」，而在人是事后重建事实，还是事前定义什么算对。

02 · 真正的瓶颈

不是 context window，是人的控制带宽

Ctotal = Cexecution + Cunderstanding + Cverification + Crecovery

AI 直接压低的只有第一项。后三项不会自动下降，session 越多反而越高。

agent 执行吞吐量  >  人的理解与验证吞吐量  ⇒  未被理解、未被验证的变化持续堆积
该优化的指标：每一单位人类注意力，换来多少「有证据、可安全接受」的工程进展。

例：agent 20 分钟写完一个数据库扩缩容功能；我花 40 分钟读代码、查它改了哪些配置、模拟器覆盖了什么、有没有碰真集群。

03 · 为什么实时监控不是答案

claude_monitor 回答的是「在不在跑」，不是「对不对」

claude_monitor（今天做的 v2）需要的
对象session / 进程task / spec
问题跑完没？卡住没？验收条件满足了几条？
recap事后让 Haiku 重建「做了啥」事前就有 spec，事后只对照
diff改了哪些文件与 spec 的差距
生命周期session 关了就没了跨 session 持久

定位

claude_monitor = kubelet / liveness probe。告诉你哪个 pod 活着、哪个在等输入。有用，但它是底层。

Spec Tracker = kubectl get 的那一层。看的是 desired vs observed。

recap 再准，也是「事后重建」，仍属于模式 A。

05 · 证据

Evidence over narration

PASS

已有符合要求的证据，证明条件满足

FAIL

已有证据，证明条件不满足

UNKNOWN

没有足够证据——包括「还没验」。
没测 ≠ 失败，更不等于通过。

Valid Evidence = Matching Version ∧ Passed Check ∧ Satisfied Preconditions
  • 「测试通过」是声明；能关联到 commit + 命令 + 退出码 + 环境 的测试结果才是证据
  • review 之后 covers 路径上又有新 commit → 之前的 PASS 不再无条件有效
  • 能交给 CI / 脚本 / 模拟器验证的，就不交给 agent 的自我评价
06 · Session ≠ Task

一个 session 多个任务，一个任务跨多个 session

这轮输入是例子动作
普通讨论解释存算分离架构直接回答，不建任务
任务细化给扩缩容加冷启动验收更新现有 spec
任务继续继续刚才的状态机恢复任务，先核对 status
新的独立任务顺便修个告警规则新建任务记录
探索比较两种扩缩容设计存结论，决定做了再建任务
重大变更改架构 / 权限 / 验收目标暂停，先改 spec 并确认

由 Task Router 判断这轮输入与已有任务的关系；有歧义、且两种理解会导致不同改动时，先问。

两层状态分开存

Session state（临时）
session_id、当前激活的 task_id、最近用过的任务

Task state（持久）
spec、验收结果、证据、偏差、下一步

关掉 Claude Code，任务不丢；同一个 session 里换话题，旧任务不被覆盖。

不是每句话都要成为任务；
是每个会改变工程状态的任务，都必须可追踪。

07 · 分级，别搞成仪式

按风险分级，映射到已有工具

级别场景要求用现有的什么
L0讨论、探索不建任务，必要时记结论—
L1局部 bug、小配置目标 + 范围 + 验证方法 + 结果轻量 scope（2–3 条 AC） ← 缺
L2多模块、状态机、跨 session完整 spec + 任务分解 + 验证harness-scope-gate + harness-openspec
L3生产、不可逆、敏感权限spec + 审批 + 独立验证scope + protected_paths gate + 人工批准
  • L1 长成 L2 时升级原记录，不另起一套
  • spec 可以改，但必须显式改、写明原因；不能因为难做就悄悄降低验收标准
  • 真正的安全边界靠权限和 gate，不靠 skill 里的一句提示词
08 · 盘点

其实已经有一半了

已有

  • .harness/scope/*.yml：goal / non_goals / acceptance_criteria / covers / risk_budget → 就是 Spec
  • harness-spec-review：无上下文 reviewer 判 CLEARED / NOT_CLEARED → 粗粒度 Status
  • oplog.jsonl：每次写操作带 session_id + git head → 执行轨迹
  • STATE.md / journal：项目级当前事实
  • harness-openspec：L2 的任务分解

缺

  • 逐条 AC 的 PASS/FAIL/UNKNOWN + 绑定版本的证据：现在 review 打的是 spec 整体分（completeness / clarity…）
  • 跨仓库的统一视图：scope 散在各仓，spec-review 是纯 pull，没人主动看全局
  • session → task 绑定：oplog 有 session，scope 不知道哪些 session 在做它
  • Task Router：scope-gate 是 opt-in，大部分活从没进过 scope
  • L1 轻量入口：写一份 scope 门槛太高

10 · 要做的东西

Spec Tracker：一个只读聚合器，不是新平台

  • 输入：所有仓库的 .harness/scope/*.yml（事实来源不变）
  • Diff 完全由 git 算：review 之后 covers 路径上的 commit 数 → 证据是否过期
  • 视图：一行一个 spec —— AC 通过 x/y、review 结论、drift、下一步、谁在做
  • 不调 LLM，不改 scope；写状态仍由 spec-review / agent 负责

三个项目的关系：

tracker · Tasks / Unscopeddesired vs observed（主视图）
tracker · Sessions（原 claude_monitor）liveness：哪个 session 在跑 / 在等我
agent_control_plane自主 agent 的 SLO / 预算 / gateway 治理

四条原则

  1. Spec before execution：先定义正确性，再允许执行
  2. Evidence over narration：信证据，不信 agent 的自述
  3. State over session：项目状态独立于对话历史
  4. Control by exception：人只看偏差、决策、高风险
10b · 这个项目到底服务什么

五种能力 = 一个任务生命周期的五段

能力Build 什么（落在哪）Tracker 每个任务量什么（可从文件算出）
Problem Framingscope yml：goal / non_goals / AC；每条 AC 带 verify: 命令AC 可执行率：带 verify 命令的 AC 占比；spec 显式修订次数
Context Engineering任务状态即上下文：SessionStart 注入 active task；STATE.md；skills / memory 检索恢复成本：新 session 第一个有效动作前花的轮数 / token；compact 次数；「做到哪了」类追问次数
Harness Engineering任务状态机（draft→confirmed→in_progress→verifying→cleared/blocked）、hooks、envelope、恢复绑定率：带 task 的写操作占比；中断续接成功率：杀掉 session 后新 session 能否接上
Verification Engineeringac_results + 绑定 commit 的证据；独立 reviewer（spec-review）；CI / 模拟器有效证据率；过期 PASS 数（review 后 covers 有 commit）；绿灯翻红次数
Delivery Ownership交付记录：改了什么、花了多少、落地后怎样；归档进 scope每任务成本（token / 时长 / session 数）；落地后回滚 / 事故；交付记录完整率

项目定位：既是这五种能力的实践载体（build 协议），也是它们的记分板（track 指标）。哪一列长期红，就是下一步该补的能力。

11 · MVP 与验收

怎么算做成了

关掉所有 session，明天打开项目，几分钟内能说清：当前状态、哪些验收已过、还有什么风险、下一步是什么——而且每一条都能追到真实证据。

分阶段

  1. 只读聚合 + 五能力记分板 （本项目，已起步）
  2. AC 带 verify:，/verify 写 ac_results（Framing + Verification）
  3. /task + oplog 带 task + 状态栏（Harness + Context）
  4. 交付记录与每任务成本（Delivery）

衡量

  • context 恢复时间 ↓
  • status 与代码 / 测试实际一致的比例
  • 已完成 AC 有有效证据的比例
  • 我追问「你做了啥 / 测了啥 / 还差啥」的次数 ↓
12 · 还没想清楚的

需要拍板的四件事

#问题倾向
Q1逐条 AC 结果谁来写？spec-review 写回 ac_results，agent 只能提交证据、不能自己判 PASS
Q2session 和 task 的绑定存在哪？oplog 每条加 task 字段；scope 不反向记录，由 tracker 聚合
Q3L1 小任务用什么载体？同一个 scope yml，只填 goal + 2–3 条 AC + covers；能升级成 L2
Q4registry：扫描还是中心索引？先扫描（零维护）；扫描慢或要跨机器时再加索引

原则：先冻结架构方向，剩下的未知项变成可验证的工程假设，在一个真实项目上试点，而不是继续停在抽象讨论里。
