# harness-cross-verify

大需求执行五段式（拆解→开发迭代→规模验证→管线→交叉验证）里的第⑤段。

这个 skill 是两个现有形状的重组，不是新发明：`harness-spec-review` 的"无上下文 reviewer + 有限轮次收敛"形状，和 `harness-explore` 的"先证明正交才并行"判断标准。区别在于审查对象——`harness-spec-review` 审的是 scope 文本本身够不够清楚/完不完整，这个 skill 审的是**实际改动/输出**是否经得起从不同角度检验，两者不是同一层，都要用。

## 步骤

### 1. 定位对象

传了 slug 就取该 child scope 关联的实际改动（diff / 部署产物 / 输出样本）。没传就取这轮自己实际动过的那部分。

### 2. 拆正交维度（复用 harness-explore 的判断标准）

先证明维度之间不重叠才拆分：**如果维度 A 的 reviewer 和维度 B 的 reviewer 会读到同一批文件/同一个判断依据，就不正交，合并成一路**。维度数量不固定，按这次改动实际暴露的风险面定，常见候选：

- 正确性——逐条对照 acceptance_criteria
- 副作用范围——有没有碰到 `covers` 之外的东西
- 运维影响——上线/回滚代价、监控盲区
- 文档/口径一致性——改动后文档、注释、对外口径是否还对得上

拆不出正交维度就减少维度数,甚至退回串行做一次综合审查，不要为了"交叉"而硬拆出会互相踩线的维度。

### 3. 并行派发无上下文 reviewer

每个维度派一个**无上下文的独立 subagent**（`Agent` 工具，不是 fork——fork 带着这轮对话的上下文，等于自己评自己，没有意义）。每个 reviewer 拿到的是实际产物本身（diff/部署配置/输出样本），不是 scope 文本，也不知道其他维度在查什么。

### 4. 合并、找矛盾（主 agent 自己做，不外包）

把各路结果拼起来，找矛盾点——不是复述每一路说了什么，是找"路 A 认为没问题的地方，路 B 从另一个角度指出了风险"这类交叉信息暴露出来的东西。写入：

```yaml
# .harness/pipeline/<slug>.yml 的 cross_validation 段
cross_validation:
  contradictions:
    - dimension_a: <维度A>
      dimension_b: <维度B>
      finding: <矛盾点是什么，谁的证据更强>
  reviewer_rounds: <n>
```

找不到对应的 pipeline artifact 就跳过落盘，只在报告里给出结论。

### 5. 相对排序，不绝对打分

**只有这一轮涉及"比较多个候选/多个并行实例的输出"时才用这条规则**（比如③规模验证的多实例方差检查结果、或④管线里比较多个候选修复方案）。这时 reviewer 只回答"给定 A 和 B，哪个更好地满足 X，为什么"，**禁止 1-10 分之类的绝对量表**。

这是和 `harness-spec-review` 的关键区别，不要默认照抄它的 5 维度打分习惯——`harness-spec-review` 判的是"这份 spec 有没有做完"，天然是绝对判定（CLEARED/NOT_CLEARED）；这个 skill 判的是"哪个更好"或"这个角度看有没有问题"，多数场景下更适合相对判断或定性发现，不是打分表。

### 6. 有限轮次收敛

有新矛盾就针对矛盾点重派一轮。最多 3 轮，**连续 2 轮没有新矛盾就停**——收敛目标是"矛盾点清单已经稳定"，不是某个类似"CLEARED"的终态。

### 7. 报告

```
【交叉核查结果】
- 对象: <slug 或改动描述>
- 维度: <维度列表>
- 轮数: <n>

【矛盾点】
- <维度A> vs <维度B>: <矛盾内容，采信哪个、为什么>（没有就留空）

【下一步】
- <矛盾点需要谁来解，或者已经可以推进到下一步>
```

## 硬规则

1. reviewer 必须是无上下文的独立 subagent，不能自评，不能用带对话历史的 fork。
2. 维度先证明正交再分派，拆不出来就减少维度数或退回串行。
3. 涉及比较场景时用相对排序，不用绝对打分——除非确认这轮不是比较场景。
4. 最多 3 轮，连续 2 轮无新矛盾就停，不是"直到没有分歧为止"。
5. 主 agent 只合并找矛盾，不代判哪个维度说的对——矛盾点记录下来交给人/后续流程处理。
