# harness-scale-check

大需求执行五段式（拆解→开发迭代→规模验证→管线→交叉验证）里的第③段。

**这个 skill 是薄先例，不是成熟机制。** 目前业界/本仓库都没有可复用的"集群规模验证"通用形态——唯一的先例是 `sre_oncall_triage_skill` 里一次性硬编码的 k8s-gate.sh 分级逻辑，样本量是 1。这份 SKILL.md 只是把那次经验里"按集群分级 allow/deny + 逐档扩大"的思路整理成一份 checklist，**没有重复使用数据支撑**。如果用过几轮发现步骤不够用或者形状不对，直接改这份文件或推倒重做，不要因为它已经是个"正式 skill"就当成定案。

## 步骤

### 1. 确认对象和 blast radius

读当前项目 `.harness/project.yml` 的 `autonomy.k8s.allow_contexts`/`deny_contexts`（如果配置了）。本次验证的执行范围**只能在 `allow_contexts` 内**——`deny_contexts` 里的集群只能作为"这次改动最终要去的地方"被引用，不能是这个 skill 实际操作的对象。

没有配置 `k8s` 段的项目，问用户：这次改动如果在最坏情况下出错，影响面是什么（几个 pod / 一个 namespace / 一个集群 / 下游依赖方）。写清楚，作为下面每一档验证的参照系。

### 2. 定最小可回退起始档位

不管最终目标规模多大，起始档位必须是"出错了立刻能撤回"的最小单位——1 个实例、1 个副本、最小流量比例。这一档的目的不是验证"扛不扛得住规模"，是验证"这东西在生产形态的环境里能不能正常工作"。

### 3. 逐档扩大清单

按项目实际情况定档位间隔（比如 1→10%→50%→100%，或 1 副本→3→10→N），每往下一档之前，**必须先完成上一档的验证**：跑完这一档该跑的验证命令（复用已有的"mutating 操作后必须跑验证"约定，不新造判定逻辑——只是把它组织成一个分档清单），确认没问题才能进下一档。不能跳档。

哪些算"验证完成"因项目而异，常见的包括：`kubectl rollout status`、错误率/延迟看板对比、日志里没有新增的 error 模式。

### 4.（可选）多实例并行方差检查

如果这次改动对并发/状态敏感（比如涉及分布式锁、幂等性、共享状态），额外起多个实例并行跑同一个改动，比较各实例的输出/指标是否一致。不是每次规模验证都需要这一步，只在改动看起来可能受并发影响时做。

### 5. 写回 pipeline artifact

```yaml
# .harness/pipeline/<slug>.yml 的 scale_verification 段
scale_verification:
  status: passed | failed | in_progress
  evidence:
    - "<每档验证的证据链接/命令输出摘要>"
  notes: >
    <哪个环境/集群、起始档位到最终档位、耗时>
```

找不到对应的 `.harness/pipeline/<slug>.yml` 就跳过这一步，不报错——这个 skill 也可以独立于 `harness-req-split` 单独使用。

### 6. 报告

```
【规模验证结果】
- 对象: <改动描述>
- 起始档位 → 最终档位: <...>
- 状态: <passed|failed|in_progress>

【证据】
- <每档的验证证据，一档一行>

【下一步】
- <如果 failed，卡在哪一档，下一步要做什么>
```

## 硬规则

1. 不代为执行扩容/发布命令本身，只提供 checklist 和记录动作——真正的 `kubectl`/`helm` 操作走已有的 `PreToolUse` envelope 和全局 `# INTENT:` 约定。
2. `deny_contexts` 里的集群不能作为这个 skill 的操作对象。
3. 每一档必须有前一档的验证证据才能推进，不能跳档。
4. 这份 checklist 是可以被推倒重做的先例，不是稳定契约——改的时候不需要走"废弃通知"那一套。
